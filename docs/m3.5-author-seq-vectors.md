# M3.5 — author_seq version vectors authoritative on the mesh

**Status:** Design for implementation (2026-06-13). Child of `sync-v2-architecture.md` §5
and `m3-lan-transport.md` §2 (deferred swap). Makes the M1 author_seq **version vector** the
SOLE completeness mechanism for the mesh anti-entropy loop (BLE + LAN), retiring the
HLC-frontier summary (`max_hlc_per_device`).

**Scope decision (user, 2026-06-13): FULL cutover, no backwards-compat.** "Go full, and
don't care about backwards compatibility — we're still building, no users yet." This is the
unlock: there is no legacy NULL-seq data to preserve, no migration-018 inferred-seq
divergence in a fresh system, and no old clients to interop with. Local data may be wiped.
A fresh system carries only **author-asserted** seqs, which dissolves the four hard blockers
the M3.5 recon found (legacy NULL rows, inferred-seq divergence, mixed-version negotiation,
HLC-coexistence). What remains is a clean, correct vector protocol.

---

## 1. The recon's verdict (why this is safe NOW but wasn't generically)

- The vector math (`lib/replication/planner.ts computeContiguous`/`provableFrontier`) is
  contiguity-correct **by construction**: the frontier is the highest `n` with `1..n` all
  present; a single hole collapses the claim. It never over-claims.
- **Server↔mobile parity is exact**: the backend `/v1/sync/vector` returns `{min,count,max}`
  per _author_ device, stamps `author_seq` verbatim from the wire (never invents), keys by
  `hlc_device_id` (the author). The mesh now does the same. No max-vs-contiguous mismatch.
- The blockers that made a _generic_ cutover unsafe were all backwards-compat artifacts:
  legacy mesh rows with `author_seq = NULL`, migration-018 backfill _inferences_ that
  diverge across replicas, and the need to keep HLC for those. **With no users, none of
  these exist** — every event is authored fresh with a canonical author_seq.

## 2. What changes

1. **`WireMeshEvent` gains `author_seq: number`** (required). It is the _author's_ canonical
   sequence, forwarded **verbatim** by every honest relay (read straight from
   `event_log.author_seq`, never re-minted).
2. **The summary message becomes a vector.** `SummaryMessage { max_hlc_per_device }` →
   `VectorSummaryMessage { type:"vector", vault_id, frontier: Record<deviceId, number> }`,
   where `frontier[device]` is the **relayable contiguous frontier** (see §3).
3. **Send is range-based, in author_seq order.** `newSendCursor`/`fetchNextBatch` (HLC-floor)
   are replaced by `planRangesToSend(localFrontier, peerFrontier)` (planner.ts) → per-(device,
   seq-range) fetch `WHERE device_id=? AND author_seq BETWEEN ? AND ?` `ORDER BY author_seq`.
4. **Ingest persists author_seq with a slot pre-check.** `insertIngested`/`insertTombstoned`
   add the `author_seq` column, mirroring the applyEvent remote-origin pre-check
   (`projection/index.ts:342-363`): if a _different_ event_id already holds the
   `(vault, author_device, seq)` slot, sacrifice the **seq** (NULL), never the event.
5. **`WIRE_VERSION` 2 → 3, `SUPPORTED_WIRE_VERSIONS = {3}`** only. No v1/v2 interop.
6. **Dropped:** `computeSummary`, `max_hlc_per_device`, `newSendCursor`, `fetchNextBatch`
   (HLC variant), and the HLC half of `countDeltaEventsFromSummary` (the wifi-upgrade volume
   estimate now counts from the vector ranges). **Kept untouched:** the `hlc_last` projection
   cursor (`HLC_LAST_KEY`, bumped per-row in ingest) — it is the projection/sweep ordering
   cursor, independent of the summary, and stays.

## 3. Relayable frontier — reconciling the relay filter

The single genuine subtlety, and the one the first review corrected. The relay filter is
`author_seq IS NOT NULL AND tombstone_reason IS NULL AND rejected_at IS NULL` — i.e. we
**FORWARD quarantined rows** (including `unknown_actor`) and withhold only tombstone/rejected.

- **Advertised `frontier[device]` = `computeContiguous` over the RELAYABLE seqs only.** The
  sender can always satisfy everything it advertises → the receiver's frontier advances
  contiguously over a relayable stream. No withheld holes. The advertise-side
  (`computeRelayableVector`) and send-side (`fetchNextBatch`) filters are byte-identical.
- **Quarantined rows are forwarded — NOT withheld.** The original design wrongly assumed
  `unknown_actor` was all-or-nothing per device (a withheld suffix). It is NOT: quarantine is
  per-event / per-HLC. A device removed at `HLC(seq 5)` quarantines only its post-removal
  events (6,7), while a role-`none` event like `account_bound` at seq 8 still applies →
  relayable, sitting ABOVE the quarantine hole. Since `author_seq` is one shared space across
  all event types for a `(vault,device)`, withholding the quarantined seqs would strand the
  relayable seq above them **permanently** (verified review finding). A quarantined event is
  validly SIGNED (only its role is unverifiable locally), so an honest relay forwarding it is
  safe — the receiver's own role-gate re-quarantines it at apply time (receipt ≠ apply), it
  never reaches the ledger, and the seq space stays contiguous. Trade-off: a removed/hostile
  device's events propagate as quarantined garbage (never applied); acceptable for kaata's
  semi-trusted-staff threat model. (Anti-spam withholding is a possible later hardening.)
- **A tombstoned (bad-sig) row is withheld and ceilings the relayable frontier** at `seq-1`.
  Rare (bad sig = corruption/forgery). We do NOT forward it (a bad copy would poison the
  receiver's event_id dedup against the good copy). The good copy propagates from the author;
  full healing awaits tombstone re-verification (a noted follow-up). Tombstoned rows are also
  persisted with `author_seq = NULL` so they cannot squat the slot the legitimate event owns.

**Send set** = events with `author_seq ∈ (peer_frontier, my_relayable_frontier]` that pass
the relay filter, ordered by `author_seq`. The receiver applies them in order; its frontier
advances to match.

## 4. Why no stranding (correctness for a fresh system)

- Honest relays forward the author's verbatim seq → two honest replicas store the same
  event_id at a given `(vault, author, seq)` slot → **no conflicts → no NULL sacrifice → no
  stranding.** The slot pre-check is defense-in-depth that should never fire in honest
  operation; it logs loudly if it does.
- The author assigns a gap-free `1..n`; in-order send means the receiver advances
  contiguously; `computeContiguous` is the watermark.
- **Gap-tolerance without explicit gap-repair:** transient/concurrency holes (multi-peer
  interleave delivering D's #6 before #5, or a mid-stream drop) leave the receiver's frontier
  pinned below the hole. The missing low range is re-sent **from `frontier+1`** on the next
  sync with any peer that holds it, and the above-hole rows the receiver already has are
  deduped. Self-healing as long as the low range is reachable somewhere — which, for events
  the author actually emitted, it is. (Permanent loss of a low seq from _every_ replica is a
  durability failure, M5's concern, not M3.5's.)

**KNOWN LIMITATION — server `seq_conflict` strip (pathological trigger).** When the server
returns `seq_conflict` for a device's OWN event (`push.ts`), that row's `author_seq` is set
NULL and the assignment floor advances past the slot, so the seq is permanently NULL and the
device's relayable mesh frontier ceilings there — every event above it is stranded from
server-offline mesh peers (they still reach the server seq-less). A `seq_conflict` on the
author's own fresh event requires the server to already hold a _different_ event in that
device's `(vault,device,seq)` slot, which only happens under **install-cloning** (copying the
app's data + identity to a second physical device) or **restore-from-snapshot** (an M5
feature not built yet — `reset` mints a fresh `install_id`, so it does NOT collide). Neither
is honest single-install operation, so §4's "no stranding" holds for the normal case. The
proper fix (decouple the local mesh seq from the server slot, or harden install identity so
clones can't collide) is deferred — it touches the M1 server-sync path and the identity model.

## 5. Trust model (and the one deferred hardening)

`author_seq` stays **unsigned** (not in `event-sig.ts SIGNED_FIELDS`). Events themselves are
Ed25519-signed by the author device, so a malicious member **cannot forge a new event from
another author** — but it _can_ alter the unsigned `author_seq` of a real event it relays
(re-stamp). A re-stamp that squats a slot makes the real event's seq get sacrificed to NULL
→ invisible to the vector → stranded. In the build phase (membership-gated, semi-trusted
shop staff, no Byzantine adversary) this is out of scope. **The clean fix is to add
`author_seq` to the signed envelope** (mobile `event-sig.ts` + backend canonical) so the seq
is tamper-proof and conflict-free — explicitly deferred as M3.5-hardening; it touches the
signing path on both codebases and is not needed before real users.

## 6. Deferred / explicitly NOT in M3.5

- **Signed author_seq** (tamper-proof, eliminates the re-stamp slot-squat) — hardening. The
  review added a wire-boundary sanitizer (`sanitizeWireAuthorSeq`: integer ≥ 1 or null) as a
  stopgap so a hostile peer's garbage can't enter the DB, but signing is the real fix.
- **`seq_conflict` mesh-strand fix** (§4 known limitation) — decouple the local mesh seq from
  the server slot, or harden install identity. Pathological trigger only.
- **Anti-spam re-withholding of removed-device events** — M3.5 now forwards quarantined rows
  for contiguity (§3), so a removed device's events propagate as never-applied quarantine.
- **Explicit gap-repair request message** — an efficiency optimization; §4 self-healing is
  already correct.
- **Tombstone re-verification on a better copy** — heals a tombstone-ceilinged frontier.
- **Epoch boundary for snapshot-restored replicas** — only reachable once M5 recovery ships;
  no restore feature exists yet, so there are no sub-snapshot gaps to mistake for holes.

## 7. Backend

**None.** The mesh is mobile↔mobile. The server already exposes/consumes author_seq vectors
(`/v1/sync/vector`, `PushEvents` stamps verbatim, keys by author) and `pull.ts`/`push.ts`
already carry author seqs on the server wire. M3.5 only rewrites the mobile mesh
anti-entropy summary/delta protocol.

## 8. Tests

- **bun (pure):** relayable-frontier computation (held-vs-relayable, `unknown_actor`
  all-or-nothing, tombstone ceiling); `planRangesToSend` against asymmetric frontiers;
  in-order send → contiguous receive; slot pre-check sacrifices seq not event. Extends the
  planner selftest or a new `lib/mesh/__dev__/vector-sync-selftest.ts`.
- **device smoke test (manual):** two phones converge a 1,000-event delta over the vector
  protocol; confirm the second sync transfers ~0 (vector populated, not re-send-everything);
  a packet capture still shows ciphertext (M3 AEAD unchanged).
