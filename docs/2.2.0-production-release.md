# Kaata 2.2.0 production release

On October 16, 2026, Matee confirmed device testing was sufficient and authorized
production releases on both stores. This supersedes the previous hold on builds
and production submission. Android must build locally because its Expo build
allowance is exhausted; iOS uses one of the two remaining Expo builds.

## Source and checks

- Release source: `3470a05a8d2f6b471a0762dbe5e2fb65fa56866e` on `main`.
- Version: `2.2.0`, Android code **59**, iOS build **39**. Both were checked
  against existing store artifacts before building.
- All **79 mobile selftest suites** and TypeScript passed. The legacy
  `person-find-selftest.ts` fixture was updated to the already implemented
  sheet selection behavior; no product behavior changed during preparation.
- Backend tests passed **674 cases/subcases** against an isolated local
  PostgreSQL cluster. The optional `TestWriteBillPreview` was skipped; no
  database-backed suite was skipped. The temporary cluster was stopped.
- The live reviewer account passed sign-in, vault listing, 30-day recovery
  policy, ownership invitation and credit permission reads. Its temporary
  session was signed out. No financial or deletion mutation was performed.
- Backend source remains identical to previously verified deployed `ab7f00c`.
  Public health is healthy. Fresh SSH/container inspection timed out; the
  authenticated feature reads provide current compatibility evidence.
- All 28 Android submission helper tests passed; the production helper also
  received an independent review and 14-test rerun.

## Builds

Android built successfully locally with the production environment, existing
Firebase client configuration, and the original EAS upload key. Its certificate matches
the previously accepted code 58 artifact:

`3275fb7365d416d147e3107b5b5ac51e4b6924ebacd18e432f5c2d6f71ab866e`

Generated native files, signing credentials, tools, logs and artifacts remain
ignored. Local build work is under `build/release-2.2.0`; no Android cloud build
was dispatched.

The first local attempt exposed Ninja 1.10.2's Windows path limitation while
building Reanimated: an existing dependency was referenced through a 261-character
path. Its timestamps were valid. The official Ninja 1.13.2 Windows archive was
verified against GitHub's published SHA-256
`07fc8261b42b20e71d1720b39068c2e14ffcee6396b76fb7a795fb460b78dc65`.
The old SDK executable was backed up and replaced; a dry run then recognized
the dependency. CMake 3.22.1, NDK 27.1.12297006 and app source were unchanged.
The local runner also switched to PowerShell 7 so compiler warnings remain
visible without being treated as terminating PowerShell errors.
The resumed build completed successfully in 20 minutes 3 seconds, with 996
actionable tasks (429 executed, 567 reused). Release lint and signing validation
passed. All 15 final artifact checks passed: package/version, release flags,
SDK levels, original upload signer, Firebase resource hashes against accepted
58, production Hermes/API settings, all four ABIs with 27 libraries each, and
16KB alignment of all 64-bit native libraries plus bundle page-alignment config.
These static checks supplement Matee's device testing; they do not inspect the
final Play-generated APK ZIP alignment.

- Artifact: `build/release-2.2.0/kaata-2.2.0-59.aab`, 94,904,727 bytes.

- Verification: `build/release-2.2.0/android59-verification/verification.json`.

iOS production build: `434b3cae-3336-4001-a145-5986c2de72e6`, using the existing
distribution certificate and provisioning profile with credentials frozen.
It was dispatched once and finished successfully at 13:30:51 UTC. The artifact
identity matched the frozen source, production/store profile and build 39.
Upload submission `3a1a231b-c325-406c-a6fc-6c15df2f41cf` was then started for

`e965cda3-a9f1-4710-be5a-b913c847f362`.

The reported missing draft icon was investigated before review submission.
The source is the correct opaque 1024px Kaata mark, with no iOS override.
The actual IPA contains correct opaque iPhone and iPad AppIcon PNGs, a compiled
asset catalog, and primary AppIcon metadata for both devices. At inspection
time the 2.2.0 draft had no attached build; its placeholder is consistent with
that state. Apple's optional icon endpoint returned HTTP 500, but the actual
binary inspection and Apple's `VALID` processing result confirmed the build
was suitable to attach without spending another Expo build.

## Store delivery

Google Play's previous image-only
update was approved and published while the builds were running. The Console
shows submission **32**, submitted October 16 at 17:25 Kabul time, as
**Published**, with managed publishing off and no pending review. No review
withdrawal was needed.

The guarded helper staged and validated internal 59, then promoted the same
bundle to production in edit `04597618124610514981`. Google confirmed the exact
artifact hash. The `ERROR_IF_IN_REVIEW` commit was acknowledged at 14:10:34 UTC,
and a fresh readback at 14:10:39 UTC verified all six preservation checks.
Only the helper's temporary verification edit was deleted. Current states:

- Production **2.2.0 (59): `IN_REVIEW`**, configured for 100% rollout after approval.
- Internal **2.2.0 (59): `PUBLISHED`**.
- Previous production **2.1.1 (50): `PUBLISHED`** until approval.
- Screenshot order/hashes, icon, listing text, app details and closed tracks preserved.
- Receipt: `docs/store-assets/.generated/store-upload/play-production-59.json`.

Apple's 2.2.0 draft already contains six new iPhone and six iPad screenshots.
They depict the new version's features and will be reviewed with that version.
After Apple confirmed build 39 as valid, that exact build was attached to the
version and release type was set to `AFTER_APPROVAL`. Apple's web form also
intermittently failed to load, so release preparation used its supported API.
A successful EAS upload alone is not an App Store submission.
The release-notes API returned HTTP 500 twice; reads confirmed the notes were
still empty. The web form recovered, saved the production notes successfully,
and accepted Add for Review. It created draft
`a01151c0-a38d-4e76-95b9-693a5d02bc9e` with `READY_FOR_REVIEW` state. The final
draft panel stalled, so the existing draft was reconciled through the API
before any final submission attempt. The UI subsequently recovered and
explicitly displayed its single item as **2.2.0 (39)**. Final **Submit for
Review** was clicked once at approximately 14:32:55 UTC. Apple acknowledged
the submission and showed **Waiting for Review** for both the version and
submission, with zero remaining draft submissions. No duplicate review was
created. Existing reviewer credentials and all 12 screenshots were retained.

- Apple review: `a01151c0-a38d-4e76-95b9-693a5d02bc9e`.
- iOS **2.2.0 (39): `WAITING_FOR_REVIEW`**, automatic release to all users after approval.
- Safe iOS receipt: `docs/store-assets/.generated/store-upload/ios-production-final.json`.
- UI evidence: `ios-production-39-review.jpg` and
  `play-production-59-review.jpg` in the same ignored upload directory.

Both production releases are submitted. As requested, work stopped at review
acknowledgement without waiting for store approval or public availability.
The release used **one iOS Expo build and zero Android Expo builds**.
